The model behind it

An auditor covers places, not postcodes

The schema currently cannot store a Dublin address, let alone match one. Three UK assumptions are baked in, and the coverage screen was quietly built on top of them.

Where the UK is hard-coded
audit.postcode — CHECK ~ '^[A-Z]{1,2}[0-9]...'
A UK postcode regex. A Dublin or Berlin address is rejected outright — this is the fatal one.
audit.postcode_area — GENERATED ALWAYS AS substring(...)
Slices the first one or two letters off a UK postcode. Means nothing anywhere else.
auditor_coverage.postcode_area — CHECK ~ '^[A-Z]{1,2}$'
Coverage can only ever be a UK postcode area.
What is true in every country
A point
Where the auditor sets out from, and where the audit happens. Every address on earth geocodes.
A willingness
How long they will travel, and how. Minutes and mode mean the same thing everywhere.
A place name
Salford. Brooklyn. Kreuzberg. Every country has human names for parts of it; only some have postcodes.

Postcode areas are none of these. They are a UK implementation detail that leaked all the way into the interface — which is why an auditor was being asked to translate "how far will I go" into geography they would have to look up.

The shape that works anywhere
TableWhat it holds
place A gazetteer row: country, name, the parent that disambiguates it ("Salford, Greater Manchester"), and a point. Seeded per country from open data — a table, not an API call.
auditor_profile base_place_id, base_point, max_travel_minutes, travel_mode. What they told us, kept as they said it.
auditor_coverage One row per place they cover, each marked derived, added or excluded. The circle proposes; the auditor confirms; we store the answer, not the guess.
audit A point, and the place_id resolved when it is booked. The postcode becomes a free-text address again, with no regex on it.
Matching stays a join

auditor_coverage.place_id = audit.place_id, excluding the rows marked excluded. No distance maths at match time, no routing service in the request path, no parsing in application code — the same properties the postcode-area join was chosen for.

The geometry runs once, on save, to propose the list. Straight-line distance with a factor per mode — crude, and honest about it on screen. Real journey times can replace that later without asking anyone anything again, because the minutes and the mode were recorded as given.

What this costs
  • A gazetteer table, seeded per country
  • Geocoding at two write points — booking, and saving coverage
  • A migration that drops two regexes and a generated column
  • Backfilling the seeded audits and coverage
What it buys
  • A second country is a seed, not a rewrite
  • The auditor never sees a code
  • Coverage becomes an explicit, queryable list rather than a fuzzy radius
  • "Nobody covers Salford for lottery" becomes answerable
Doing it now, or later

Later is more expensive than it looks. Every seeded audit, every auditor's coverage and every matching test is written against postcode areas today — and the longer real audits accumulate against a UK-only column, the more there is to backfill and the more history there is to get wrong.

Doing it now is one migration, one gazetteer seed and a rewrite of eligible_auditors. There are eleven audits in the database and two real auditors.
